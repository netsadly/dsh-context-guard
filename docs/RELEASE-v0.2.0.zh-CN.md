# v0.2.0：自动识别模型类型与原生图片支持

本次在 v0.1.2 上新增以下行为，保留已有摘要来源校验、系统提示保护和分词排队修复。

## 实际改动

- 每次预算检查重新查询准确的已加载模型，接受具备文本能力的 llm 和 vlm。修复视觉模型已加载却被误报为“Exact text model must already be loaded”的问题。普通文字请求可随模型类型切换；不自动加载或替换模型。
- qwen35 视觉模型保留 Harness 原生图片附件传输。分词使用独立的文字投影，按实际请求图片尺寸另加保守视觉预留；预检和最终发送同时检查。该估算不是精确的视觉 tokenizer。
- 图片历史不交给文字摘要器。选择可压缩前缀时保护图片节点、工具配对和后面只有运行时通知的最新人工请求；有实际助手或工具进展后，已完成的文本历史仍可压缩。
- 不识别的视觉架构仍可用文字；发送图片会明确拒绝。无效附件、未加载或不明确的模型、未知实际容量继续拒绝。

## 验收和边界

- 本机 Harness 0.2.1-rc.5 新建标准模式会话，实际发送 640×360 合成图片；正确识别 VISION 7429、从左到右的红色正方形和蓝色圆形，约 6 秒完成。思考保持开启。没有发布该会话或原始日志。
- 发布前对合入后的版本重新运行完整自动化、原生宿主及两项真实模型摘要测试；具体结果见 VALIDATION.md。合成测试不等于全部视觉架构、图片尺寸或复杂工具任务均已通过。
- 图片历史仍不能自动摘要；超出实际加载容量时会保护性停止，可能需要新会话。全新 Windows 安装验收仍未完成。
- 本次另发现宿主的粗略输入估算曾把输出上限压到 1 token。本机把模型能力元数据与实际加载容量分开后恢复输出；插件仍逐次按真实加载容量守护。该机器专属配置不在发布包中，不应把能力上限误当作已分配内存，关闭保护插件后也不能依赖其预算检查。
- 思考后以 EOS 结束、没有正文的问题已复现，但本版没有修复它。此问题与输出上限被压到 1 token 不同。后续将保留思考能力进行独立修复和复杂任务验收。

## 包内容和升级

发布包只含插件源码、通用配置、说明与合成测试，不含 SDK、宿主模块、模型、私人会话、检查点、日志或机器专属安装产物。它是源码包，不是双击安装包。

按 README 准备 SDK 后，重新运行 scripts/prepare-local.mjs 生成本机安装目录；会话空闲时重载插件或重启 Harness，并确认插件运行。不要将别人的 private/local-plugin 直接复制到本机使用。
